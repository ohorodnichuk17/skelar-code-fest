# Resolver

### Автоматизація підтримки користувачів SaaS-продуктів

Хакатонний проєкт команди на **PolyTech Code Fest × SKELAR**. Завдання — **AI Customer Support Automation**.

Ми створили Resolver, щоб автоматизувати перевірку типових звернень про оплату та доступ. Агент аналізує повідомлення, перевіряє журнали сервісу й готує або виконує відповідну дію. Оператор бачить, на чому ґрунтується рішення, і погоджує повернення коштів.

## Проблема

«З мене списали двічі», «Я оплатив, але послуга не працює», «У мене є підписка, але немає доступу».

Щоб розібратися з такими зверненнями, підтримка перевіряє платежі, стан підписки та журнали подій. Ми зосередилися на автоматизації цих перевірок і зрозумілому поясненні результату.

## Наше рішення

Resolver поєднує аналіз звернення через **Gemma** із серверними правилами виконання операцій.

- Знаходить інструкцію для конкретного випадку.
- Зіставляє скаргу з платежами та журналами.
- Активує оплачену послугу або відновлює доступ, якщо перевірки пройдено.
- Готує повернення дубльованого платежу на погодження оператору.
- Блокує операцію, якщо проблема не підтверджується.
- Обмежує дані, які отримує модель, залежно від компанії та дії.
- Створює чернетки інструкцій для нових випадків із подальшим погодженням людиною.

**Модель пропонує рішення, а сервер перевіряє, чи дозволено його виконати.**

## Що показуємо в демо

Для двох SaaS-продуктів — **FitPulse (Україна)** та **StudyDesk (Німеччина)** — підготували п’ять сценаріїв.

| Звернення | Результат |
| --- | --- |
| Подвійне списання | Журнали підтверджують дубль. Повернення другого платежу очікує погодження оператора |
| Оплачена послуга неактивна | Агент перевіряє оплату та повторно активує послугу |
| Немає доступу за чинною підпискою | Агент перевіряє право доступу та відновлює його |
| Заявлене блокування входу | Журнали показують успішний вхід. Операція блокується, потрібні уточнення |
| Списання після скасування | Журнали не підтверджують новий платіж. Повернення не виконується |

Отже, три випадки підтверджуються журналами й мають різні шляхи вирішення, а два — демонструють відмову від необґрунтованої дії.

У вкладці доступу до даних можна перевірити, які поля дозволені для обраної операції. Для нестандартного звернення оператор може описати перевірене рішення та створити на його основі нову інструкцію.

## Технології

- **Backend:** C#, .NET 10, ASP.NET Core, Carter, MediatR, FluentValidation.
- **Frontend:** React 19, TypeScript, Vite, CSS.
- **AI:** Gemma через Google Generative Language API.
- **Дані:** демонстраційний стан у пам’яті; EF Core InMemory у попередньому модулі звернень.

## Поточний стан

Resolver — робочий хакатонний прототип із реальною мовною моделлю та змодельованими даними компаній. Дії змінюють стан у пам’яті, який скидається після перезапуску. Реальні платежі й сторонні сервіси не підключені.

Профілі країн демонструють механізм обмеження доступу. Нові погоджені інструкції повторно використовуються для того самого нормалізованого звернення без перенавчання моделі.
